# Секреты: SOPS + age

Документ описывает этап 0.2 [архитектурного плана](ARCHITECTURE_PLAN.md):
хранение секретов в Git только в зашифрованном виде через
[SOPS](https://github.com/getsops/sops) и [age](https://github.com/FiloSottile/age).
Реализованы правила, скрипты и проверки. **Реальных секретов, ключей и
публичного recipient оператора в репозитории нет**; они появятся отдельными
изменениями. VPN по-прежнему не реализован и не развёрнут.

## Модель угроз

Защищаемся от:

- публикации открытого текста секретов в публичном репозитории, истории Git,
  логах CI, PR и issue;
- случайного коммита приватного ключа age или расшифрованного файла;
- доступа CI и сторонних участников к содержимому секретов.

Не защищаемся от:

- компрометации рабочей машины оператора или самого приватного ключа;
- раскрытия **имён** ключей и структуры YAML: SOPS шифрует только значения;
- анализа размера и времени изменения зашифрованных файлов.

Отсюда правило: имена ключей и структура не должны сами быть секретом.

## Разрешённые файлы в secrets/

| Путь | Требование |
| --- | --- |
| `secrets/README.md` | Единственный файл в открытом виде. |
| `secrets/**/*.sops.yaml`, `secrets/**/*.sops.yml` | Структурно зашифрованный SOPS YAML. |
| Любой другой путь в `secrets/` | Запрещён. |

Зашифрованный файл считается корректным, если:

- есть верхнеуровневый mapping `sops`;
- `sops.age` — непустой список записей с публичным recipient `age1...` и
  зашифрованным блоком `enc`; placeholder-получатели отклоняются;
- `sops.mac` — непустая строка `ENC[...]`, `sops.version` — непустая строка;
- каждое значение вне `sops` — строка вида `ENC[...]`; комментарии допускаются
  только зашифрованные (`#ENC[...]`).

Нигде в репозитории не допускаются `*.plain`, `*.decrypted`, `*.decrypted.*`,
`*.agekey`, `keys.txt`, `*.key`, `*.pem` и полный приватный ключ age в
содержимом файлов.

## Ключ оператора

Приватный ключ создаётся **вне репозитория** и не передаётся в CI:

```sh
mkdir -p ~/.config/sops/age
chmod 700 ~/.config/sops/age
age-keygen -o ~/.config/sops/age/keys.txt
chmod 600 ~/.config/sops/age/keys.txt
```

`age-keygen` выводит в stderr только публичный ключ. Не открывайте `keys.txt`
на экране и не копируйте его в чаты, issue и PR.

SOPS ищет приватный ключ сам: `SOPS_AGE_KEY_FILE`, `SOPS_AGE_KEY` или
стандартный `keys.txt` — `~/.config/sops/age/keys.txt` на Linux
(`$XDG_CONFIG_HOME/sops/age/keys.txt`, если переменная задана) и
`~/Library/Application Support/sops/age/keys.txt` на macOS. Скрипты
репозитория ключ не читают и не выводят.

## Публичный recipient

Recipient — публичный ключ `age1...`, его можно публиковать:

```sh
export SOPS_AGE_RECIPIENT="$(age-keygen -y ~/.config/sops/age/keys.txt)"
```

Несколько получателей (например, основной ключ и резервный) перечисляются
через запятую без пробелов.

В [.sops.yaml](../.sops.yaml) recipient намеренно не указан: правило
`creation_rules` только задаёт область `secrets/**/*.sops.y*ml`, а
`scripts/secrets/encrypt.sh` всегда передаёт получателя явно через
`--age "$SOPS_AGE_RECIPIENT"`. Без `--age` SOPS завершается ошибкой
«empty key group provided», поэтому новый файл нельзя случайно зашифровать на
неизвестный ключ. Если позже recipient будет добавлен в `.sops.yaml`, проверка
отклонит placeholder и некорректный формат.

## Шифрование

Исходный YAML создаётся вне репозитория, например во временном каталоге с
правами `700`:

```sh
scripts/secrets/encrypt.sh /path/outside/repo/app.yaml
```

Скрипт:

- требует `sops` и `SOPS_AGE_RECIPIENT`, проверяет формат `age1...`;
- отказывается шифровать файл, уже находящийся в `secrets/`;
- пишет `secrets/<имя>.sops.yaml` (из `app.yaml` получится
  `secrets/app.sops.yaml`); существующий файл перезаписывает только с `--force`;
- работает с `umask 077`, запускает
  `sops --encrypt --age "$SOPS_AGE_RECIPIENT" --input-type yaml --output-type yaml`;
- проверяет результат `scripts/secrets/check_sops.py` и публикует его в
  `secrets/` только при успехе; иначе удаляет результат.

После шифрования удалите исходный YAML, просмотрите diff и добавьте файл в
индекс: `git add secrets/app.sops.yaml`, затем `make check`.

## Расшифровка

```sh
scripts/secrets/decrypt.sh secrets/app.sops.yaml
scripts/secrets/decrypt.sh --output /path/outside/repo/app.yaml secrets/app.sops.yaml
scripts/secrets/decrypt.sh --output /path/outside/repo/app.yaml --force secrets/app.sops.yaml
```

По умолчанию вывод идёт в stdout. С `--output` файл создаётся с правами `600`
и только за пределами репозитория; существующий файл перезаписывается лишь с
`--force`. Для изменения значений удобнее `sops edit secrets/app.sops.yaml`:
SOPS расшифровывает файл во временный каталог и шифрует обратно для тех же
получателей.

## Проверки и CI

- `make secrets-check` и `python scripts/secrets/check_sops.py` — структурная
  проверка путей и содержимого из индекса Git. Untracked-файлы не читаются.
- `make check` запускает `secrets-check` после pre-commit, поэтому политику
  обеспечивает и обязательный job `Repository checks`.
- `scripts/secrets/check.sh` — то же плюс `sops filestatus` для каждого
  tracked-файла, если `sops` установлен. Расшифровки нет.
- Workflow `Secrets policy` (job `SOPS policy`) запускает unit-тесты
  `scripts/secrets/tests` и `check_sops.py`.

CI **никогда не расшифровывает** секреты: в нём нет `sops`, ключа age,
секретов GitHub и прав записи. Причина — публичный репозиторий и PR из
форков: любой ключ в CI стал бы доступен коду из PR. Проверка структуры не
требует ключа и ловит главные ошибки — открытый текст, отсутствие метаданных,
ключи в репозитории. Корректность самих значений проверяет оператор при
расшифровке на своей машине.

## Резервная копия и потеря ключа

- Приватный ключ — единственный способ расшифровать секреты. При потере всех
  копий ключа зашифрованные файлы невосстановимы; секреты придётся выпустить
  заново у каждого сервиса.
- Храните минимум одну офлайн-копию `keys.txt` (например, зашифрованный
  носитель или менеджер паролей) отдельно от рабочей машины.
- Альтернатива — второй, резервный ключ age, хранящийся офлайн: добавьте его
  публичный recipient во все файлы (`SOPS_AGE_RECIPIENT` через запятую или
  `sops rotate --add-age`).

## Ротация

Плановая смена ключа оператора:

1. Создайте новый ключ вне репозитория и получите его recipient.
2. Для каждого файла добавьте новый recipient, удалите старый и смените ключ
   данных:

   ```sh
   sops rotate --in-place --add-age age1NEW... --rm-age age1OLD... secrets/app.sops.yaml
   ```

3. Проверьте расшифровку новым ключом, выполните `make check`, откройте PR.
4. После слияния уничтожьте старый ключ и все его копии.

`sops updatekeys` при текущем `.sops.yaml` без recipient завершается ошибкой
«empty key group provided» и ничего не меняет; используйте `sops rotate`.

Ротация ключа age не меняет сами секреты: если есть подозрение, что старое
значение раскрыто, выпустите новые значения (см. ниже).

## Компрометация

Если приватный ключ age или открытый текст секрета мог быть раскрыт:

1. Считайте раскрытыми **все** значения, когда-либо зашифрованные для этого
   ключа: история Git хранит старые версии файлов.
2. Отзовите и перевыпустите затронутые секреты у самих сервисов (пароли,
   токены, ключи API). Это production-действие и требует отдельного явного
   разрешения владельца.
3. Создайте новый ключ age, перешифруйте файлы с новыми значениями
   (`sops rotate` или повторный `encrypt.sh --force`), откройте PR.
4. Если открытый текст попал в Git, удаление файла в новом коммите его не
   скрывает; переписывание опубликованной истории запрещено правилами
   репозитория, поэтому единственная защита — перевыпуск секрета.
5. Сообщайте о раскрытии приватно по [SECURITY.md](../SECURITY.md), без деталей
   в публичных issue и PR.
